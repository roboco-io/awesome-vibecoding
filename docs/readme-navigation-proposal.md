# README 탐색 구조 개선안

목표는 소프트웨어 개발자와 개발자 지망생이 바이브 코딩에 필요한 최신 정보를 빠르게 찾도록 하는 것입니다. 이 문서는 변경 전 README를 분석한 승인된 설계 기록입니다. 2026-09-18에 작업별 분류와 탐색 구조를 적용했으며, 아래 규모 수치는 변경 전 기준입니다.

**핵심 방향: 작업 목적을 기본 분류로 삼고, 최신성·이용 조건·도구 형태를 보조 정보로 제공합니다.**

## 현재 구조의 문제

현재 README는 492줄이며 주요 도구 분류는 다음과 같습니다. MCP는 여러 리소스를 한 행에 묶으므로 다른 분류와 행 수를 직접 비교하면 규모가 작아 보입니다.

| 현재 분류 | 항목 규모 | 탐색 문제 |
|---|---:|---|
| IDE & Editor Assistants | 61개 도구 | IDE, CLI, 리뷰 도구, 설정 도구, 사용량 모니터가 한 표에 섞입니다. |
| Agentic Coding Environments | 35개 도구 | 코딩 에이전트, 실행 환경, 명세 도구, 범용 에이전트 프레임워크를 구별하기 어렵습니다. |
| MCP Servers & Tooling | 21행, 43개 링크 | 프로토콜을 기준으로 묶어 테스트·배포·문맥 검색이라는 실제 용도가 가려집니다. |
| Cloud & Platform Integrations | 37개 도구 | 앱 생성, UI 생성, 호스팅, 범용 AI 앱 플랫폼이 함께 나옵니다. |

IDE는 사용 형태, agentic은 동작 방식, cloud는 실행 위치, MCP는 연결 규격입니다. 분류 축이 달라 한 도구가 여러 곳에 들어갈 수 있습니다. 제품이 기능을 추가할 때마다 분류가 흔들리기도 합니다.

학습 자료도 논문·글·영상 순서로 나뉘어 있습니다. 처음 방문한 학생은 어떤 자료가 첫 실습에 적합한지, 경험 있는 개발자는 어떤 자료가 당장의 디버깅에 필요한지 직접 판단해야 합니다. 또한 추가·변경·종료 정보가 따로 없어 재방문자가 전체 목록을 다시 읽어야 합니다.

## 권장 목차

```text
한 문장 소개 + 빠른 이동
최근 확인된 변경
처음 시작하기
작업별 도구 찾기
  1. 코드 작성·수정
  2. 앱·UI 프로토타이핑
  3. 문맥·명세·도구 연결
  4. 테스트·리뷰·보안
  5. 배포·실행 환경
  6. 에이전트 작업환경·사용량 관리
배우고 실습하기
  첫 프로젝트 따라 하기
  실무 문제 해결·워크플로
  개념·원리·연구
커뮤니티·관련 목록
등록 기준·기여·라이선스
```

상단 빠른 이동은 세 경로면 충분합니다.

| 독자 | 질문 | 바로 연결할 곳 |
|---|---|---|
| 학생·입문자 | 처음 무엇부터 해야 하나요? | 선수 지식, 첫 실습, 비용을 포함한 시작 안내 |
| 개발자 | 지금 하려는 작업에 어떤 도구가 필요한가요? | 여섯 작업별 도구 분류 |
| 재방문자 | 지난번 이후 무엇이 달라졌나요? | 검증된 변경 요약 |

독자별로 전체 도구 목록을 복제하지 않습니다. 같은 항목으로 연결하는 서로 다른 진입 경로를 제공합니다. GitHub는 제목 기반 목차와 섹션 링크를 제공하므로 별도 웹사이트 없이 구현할 수 있습니다. [GitHub README 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)

## 작업별 도구 분류와 이동 예시

아래 예시는 현재 README에 적힌 용도를 기준으로 한 분류 제안입니다. 각 제품의 기능 전체를 새로 검증했다는 의미는 아닙니다.

| 권장 분류 | 독자가 찾는 것 | 기존 항목 이동 예시 |
|---|---|---|
| 코드 작성·수정 | 기존 코드 이해, 기능 구현, 리팩터링 | Cursor, Claude Code, Codex CLI, Aider, OpenHands |
| 앱·UI 프로토타이핑 | 화면이나 앱의 초기 형태 만들기 | Lovable, Bolt.new, v0, Dyad |
| 문맥·명세·도구 연결 | 요구사항, 프로젝트 규칙, 외부 문서·데이터 연결 | OpenSpec, Context7, Caliber, 설정·스킬 모음, Git/DB 관련 MCP |
| 테스트·리뷰·보안 | 생성한 코드 검증과 회귀 방지 | Qodo, PR-Agent, Agent QA, Semgrep, Playwright MCP |
| 배포·실행 환경 | 결과물 게시, 격리 실행, 실행 인프라 연결 | Publish.my, E2B, Vercel MCP, Cloudflare MCP |
| 에이전트 작업환경·사용량 관리 | 여러 세션 관리, 작업 관찰, 비용·할당량 확인 | Duckweed, Superagent, Parallel Code, llm.log, usage, Agent Island, NextReset |

Superagent처럼 코딩 기능도 있고 작업환경 역할도 하는 경우, 독자가 그 제품을 찾는 주된 목적 하나를 기준으로 배치합니다. 다른 곳에는 설명을 반복하지 않고 필요한 경우 해당 항목으로 연결합니다.

MCP는 독립적인 주 분류에서 연결 방식 표시로 바꿉니다. 예를 들어 Context7과 Playwright MCP는 모두 MCP이지만, 전자는 문맥·문서, 후자는 테스트에서 찾게 합니다. MCP만 보고 싶은 독자를 위해 별도 색인 링크를 둘 수 있습니다.

범용 AI 앱 플랫폼·챗봇 프레임워크·개인 비서는 별도로 재심사합니다. 바이브 코딩으로 소프트웨어를 개발하는 도구와 AI 기능을 가진 앱을 만드는 프레임워크는 독자의 목적이 다를 수 있습니다. 직접적인 개발 워크플로가 확인되는 항목은 남기고, 인접 분야의 참고 자료는 확장 목록으로 분리하는 편이 좋습니다. 단순히 카테고리가 맞지 않는다는 이유만으로 일괄 삭제하지는 않습니다.

## 학습 자료는 매체보다 학습 목적을 먼저 보여줍니다

`Research Papers → Articles → Videos` 순서를 다음처럼 바꾸는 것을 권합니다.

| 학습 목적 | 자료에 표시할 정보 | 연결할 기존 내용 |
|---|---|---|
| 첫 프로젝트 따라 하기 | 선수 지식, 예상 시간, 완성 결과물, 실제 비용 조건 | 입문 튜토리얼, handbook, starter kit |
| 실무 문제 해결 | 해결할 문제와 적용 단계 | 신규 기능·리팩터링·버그 수정·테스트 워크플로, 보안 가이드 |
| 개념·원리·연구 | 다루는 개념, 읽기 난도, 발행·확인 시점 | MCP 설명, context engineering, 논문·벤치마크 |

글·영상·논문, 한국어·영어·일본어는 항목의 보조 표시로 남깁니다. 학생에게는 논문보다 완성 가능한 첫 실습이 먼저 보여야 합니다. 숙련 개발자에게는 긴 입문 과정을 거치지 않고 문제 해결 자료로 이동하는 경로가 필요합니다.

학습과 작업 해결, 참고와 설명을 독자의 서로 다른 요구로 나누는 접근은 [Diátaxis](https://diataxis.fr/)와도 맞습니다. 이 저장소에서는 그 분류를 그대로 강제하기보다 큐레이션 목록에 맞게 단순화하는 편이 적절합니다.

기존 `Workflows & Templates`와 `Best Practices`는 실무 문제 해결 구역에서 함께 찾게 합니다. `Community > Starter Kits`에 있는 템플릿·설정 모음은 첫 실습 또는 문맥·규칙 구역으로 이동합니다. `Domain Applications`의 웹·모바일·데이터 구분은 중복된 목록을 만들기보다 필요할 때만 보조 표시로 사용합니다.

## 최신성을 찾을 수 있는 정보로 만듭니다

상단에는 최근 30일의 의미 있는 변경 5–10건만 보여주는 방안을 권합니다. 기준은 새로 등록된 항목, 실제 기능·이용 조건 변경, 이름·공식 URL 변경, 종료·보관 처리입니다. 변화가 없으면 과거 소식을 최신 소식처럼 다시 올리지 않습니다.

세 날짜의 의미를 구별해야 합니다.

| 정보 | 뜻 | 주의점 |
|---|---|---|
| 등록일 | 이 목록에 처음 들어온 날 | 도구 출시일이 아닙니다. |
| 마지막 확인일 | 근거를 보고 설명·상태를 검증한 날 | README 커밋 시각이나 링크 HTTP 200 확인일로 대체하지 않습니다. |
| 원문 발행·릴리스일 | 인용한 문서나 제품 변경의 실제 날짜 | 새로 발견한 오래된 자료를 신제품으로 오인하지 않게 합니다. |

검증 기록이 없는 기존 항목은 `확인 기록 없음`으로 시작합니다. 오늘 전체 목록의 확인일을 일괄 갱신하면 최신성 표시의 신뢰가 무너집니다. 별 수·다운로드 수·특정 모델 버전처럼 쉽게 낡는 수치는 필수 용도 설명에서 빼거나 근거 날짜를 붙입니다.

종료된 도구는 기본 목록에서 계속 추천하지 않고 보관 목록으로 이동합니다. 대체 이름이나 후속 프로젝트를 확인한 경우 연결합니다. 일시적으로 접근이 차단된 항목은 종료로 단정하지 않고 검토 대상으로 남깁니다.

## 표는 비교에 필요한 정보만 담습니다

기본 표는 `리소스 | 언제 쓰는가 | 이용 조건 | 마지막 확인` 정도의 네 열을 권합니다. 넓은 표를 피하려고 플랫폼·인터페이스·라이선스 전부를 각각 독립 열로 만들지는 않습니다. 중요한 제약만 간단한 표시로 넣고 상세 정보는 항목 설명이나 별도 문서에서 제공합니다.

- 도구 형태: IDE, CLI, Web, Desktop, MCP 등.
- 이용 조건: 무료 이용 가능, 무료 한도, 유료, BYOK 등. 무료 CLI라도 모델 API 비용이 들면 이를 구별합니다.
- 라이선스: 오픈소스와 소스 공개형 제한 라이선스를 구별합니다. 라이선스는 가격 표시의 대체물이 아닙니다.
- 학습 자료: 언어, 대상 수준, 실습 시간 또는 선수 지식. 시간은 실제로 검증하거나 저자의 안내임을 명시합니다.

도구 이름만으로 초급·중급을 단정하지 않습니다. 난도는 필요한 환경과 해당 자료의 선수 지식으로 설명하는 편이 학생에게 더 유용합니다. 기능 설명은 홍보 문구보다 “기존 저장소에서 PR 검토”, “브라우저에서 UI 시안 생성”처럼 사용 상황을 먼저 씁니다.

카테고리 안에서는 기본적으로 이름순을 사용해 위치를 예측할 수 있게 하고, 최신 항목은 상단 변경 요약에서 찾게 합니다. 계속 새 항목을 표 끝에 붙이는 방식은 발견 순서를 분류처럼 만들기 때문에 피합니다.

## README에서 줄일 내용

자동화 아키텍처와 워크플로 설명은 현재 약 66줄을 차지합니다. 이미 존재하는 `docs/automation.md`로 모으고 README에는 운영 방식 한 문장과 링크만 남기는 편이 독자 목적에 맞습니다. 학생과 개발자가 리소스를 찾기 위해 저장소의 내부 파이프라인부터 이해할 필요는 없습니다.

밈 이미지와 긴 개념 설명은 빠른 이동 링크보다 아래에 두거나 축약합니다. 첫 화면에서는 이 목록의 목적, 최신 확인 정보, 시작·작업·변경 경로가 먼저 보여야 합니다.

## 적용 순서와 확인 방법

1. **탐색 경로 정리:** 상단 세 경로를 만들고 IDE 표를 여섯 작업 분류로 재배치합니다. 기존 링크는 보존하고 중복 설명만 정리합니다.
2. **학습 경로 정리:** 첫 실습·실무 해결·원리/연구로 자료를 재분류하고 커뮤니티 안의 starter kit을 옮깁니다.
3. **최신성 표시 도입:** 신규·변경 항목부터 확인 날짜와 근거를 기록하고 최근 변경 요약을 만듭니다. 기존 항목은 순차적으로 재검증합니다.
4. **자동화와 번역 동기화:** 이슈 양식의 카테고리, 주간 `CATEGORY` 값, 프롬프트, 표 형식 검사, 번역 위치를 함께 바꿉니다. README 제목만 바꾸면 새 이슈가 다시 잘못 분류될 수 있습니다.

제안하는 탐색 목표는 다음 세 질문에 30초 안에 목적지 링크를 찾는 것입니다. 이는 개선 후 확인할 목표이며 현재 측정한 성능 수치는 아닙니다.

- 학생: “추가 API 비용 조건을 확인하고 첫 프로젝트 실습을 시작하고 싶다.”
- 개발자: “기존 저장소의 AI 코드 리뷰·테스트 도구를 찾고 싶다.”
- 재방문자: “최근 한 달에 무엇이 바뀌었고 어떤 항목을 다시 확인해야 하나?”

첫 적용에서는 별도 사이트나 복잡한 검색 시스템 없이 Markdown 목차, 작업 분류, 일관된 표시부터 정리하는 것을 권합니다.
