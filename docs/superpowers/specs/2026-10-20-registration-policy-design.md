# 등록 요청 자동 처리 정책 설계

- 작성일: 2026-10-20
- 상태: 초안 (메인테이너 검토 대기)
- 관련 문서: `docs/curation-policy.md`, `docs/automation.md`, `scripts/lib/categories.mjs`, `data/catalog-status.json`

## 1. 배경과 목적

awesome-vibecoding은 GitHub 이슈로 리소스 등록 요청을 받는다. 이슈가 생성되면 `auto-process-issue.yml` 워크플로가 Pi agent와 Exa 검색으로 요청을 검토하고, 조건을 충족하면 README.md, README.ko.md, README.ja.md에 항목을 추가한다. 판단할 수 없으면 `needs-review` 라벨을 붙이고 메인테이너의 `/approve` 또는 `/reject`를 기다린다.

2026-10-20 기준으로 열린 등록 요청 7건(#47, #49, #53, #54, #55, #56, #58)이 모두 `needs-review` 상태로 멈춰 있다. 봇 코멘트를 분석한 결과, 막힌 이유는 품질 문제가 아니라 정책 공백이다. 첫째, #49, #55, #56, #58은 봇이 5개 필수 조건을 모두 통과했다고 판단했지만, 해당 카테고리의 README 정원(shortlist limit)이 가득 차 있었다. 현재 정책은 정원이 찼을 때 "교체는 편집 판단"이라고만 규정하므로 자동화가 멈췄다. #47도 같은 Context 카테고리이므로 같은 이유로 추정한다(봇 코멘트에서 직접 확인하지 않음). 둘째, #53과 #54는 사이트가 생긴 지 얼마 되지 않아 Exa 검색 색인에 없었다. 현재 규칙은 증거 URL이 이번 실행의 Exa 검색 결과에 포함되어야 한다고 요구하므로, 제출자가 준 링크만으로는 증거가 되지 않았다.

이 설계의 목적은 두 가지다. 하나는 정책 요건을 충족하는 요청을 사람의 개입 없이 끝까지 처리하는 것이다. 다른 하나는 사람의 판단이 실제로 필요한 경우를 명확한 목록으로 정의하는 것이다. 실행 구성은 DeepSeek(모델) + Pi agent(에이전트) + Exa(조사)이다.

## 2. 목표, 비목표, 실패 조건

**목표.** 5개 필수 조건을 통과한 요청은 README, 확장 목록(`docs/verified-catalog.md`), 또는 README 교체 중 하나로 자동 처리되고 이슈가 닫혀야 한다. 수동 승인으로 넘어가는 요청은 이 문서 5절의 사유 중 하나를 코멘트에 명시해야 한다. 정책 확정 후 대기 중인 7건을 새 파이프라인으로 재처리한다.

**비목표.** 기존 5개 필수 조건 자체를 완화하거나 다시 설계하지 않는다. 주간 업데이트(`weekly-update.yml`)의 동작은 모델 기본값 변경 외에는 바꾸지 않는다. 기존 README 항목 전체를 일괄 재검토하지 않는다.

**실패 조건.** 다음 중 하나가 발생하면 기술적으로 동작하더라도 실패로 본다. 사람이 고른 유효한 README 항목이 모델의 주관적 판단만으로 밀려나는 경우. 증거가 제출자의 주장뿐인 리소스가 자동 등록되는 경우. 같은 카테고리에서 새로 들어온 항목이 곧바로 다시 교체되는 연쇄 교체가 일어나는 경우. 수동 승인으로 보낸 요청이 `/approve` 후에도 같은 사유로 다시 보류되는 경우.

## 3. 자동 등록 정책

### 3.1 필수 조건 (기존 유지)

`docs/curation-policy.md`의 5개 필수 조건(직접 관련성, 검증 가능한 증거, 차별성, 투명성, 유지보수)과 `available_to_new_users`, `not_sunsetting` 검사는 그대로 적용한다. 이 7개 검사를 모두 통과한 요청만 자동 처리 대상이 된다. 하나라도 실패하면 기존 정책대로 거절하거나 수동 승인으로 보낸다.

### 3.2 증거 인정 범위 (변경)

자동화는 Exa 검색 결과뿐 아니라 제출자가 제공한 URL을 Exa의 URL 읽기 기능(`web_fetch_exa` 또는 Pi custom tool의 동등 기능)으로 직접 읽은 결과도 증거로 인정한다. 이렇게 하는 이유는 검색 색인이 신생 사이트를 따라가지 못해 정상 요청이 보류되기 때문이다.

다만 제출자가 통제하는 페이지만으로는 자동 등록하지 않는다. 직접 읽은 제출 URL을 증거로 쓰는 경우, 제출자와 독립된 출처를 1개 이상 함께 확인해야 자동 등록한다. 독립 출처로 인정하는 범위는 다음과 같다. 이 범위는 설계자가 제안했고 메인테이너가 2026-10-20에 확정했다. 공개 소스 저장소(GitHub, GitLab 등)에서 실제 코드나 릴리스가 확인되는 경우, 패키지 레지스트리(npm, PyPI, crates.io, VS Code Marketplace, MCP registry 등)에 게시된 경우, 그리고 Exa 검색이 반환한 제3자 페이지가 해당 리소스를 언급하는 경우다. 제출자의 저장소라도 실제 코드와 릴리스 이력이 있으면 독립 출처로 인정한다. 이 판단은 저장소가 존재한다는 사실이 아니라, 저장소가 마케팅 문구와 별개로 검증 가능한 산출물을 담고 있는지에 근거한다.

독립 출처가 없으면 수동 승인으로 보낸다(5절의 "근거 충돌·조건 불명확" 사유). 직접 읽기에 실패한 경우(403, 429, 5xx, 시간 초과)는 기존 정책대로 리소스가 무효라는 증거로 보지 않고 수동 승인으로 보낸다.

### 3.3 배치 결정

7개 검사를 통과한 요청은 다음 순서로 배치 위치를 정한다.

1. 해당 카테고리의 README 항목 수가 정원(`scripts/lib/categories.mjs`의 `limit`) 미만이면 README에 추가한다.
2. 정원이 찼으면 3.4절의 교체 검토를 수행한다. 교체 조건을 충족하면 README의 기존 항목을 교체한다.
3. 교체 조건을 충족하지 못하면 `docs/verified-catalog.md`의 해당 카테고리에 추가하고 이슈를 닫는다. 이슈 코멘트에는 확장 목록에 등록되었다는 사실과 README에 들어가지 못한 이유(어떤 교체 조건을 충족하지 못했는지)를 적는다.

세 경우 모두 이슈를 닫는다. 확장 목록 등록도 정상 처리 완료로 본다.

자동으로 등록하는 항목의 증거는 이슈의 봇 코멘트에 기록한다. 이 규칙은 README 항목과 확장 목록 항목에 똑같이 적용된다. 봇 코멘트에는 7개 검사 결과, 증거 URL, 점수를 적는다. 기존 확장 목록 행의 "Verified" 열은 `lifecycle-review-2026-09-18.md`의 앵커로 연결된다. 반면 새로 자동 등록하는 행의 "Verified" 열은 검증 날짜를 표시하고 해당 이슈 URL로 연결한다(설계자 판단). 따라서 별도의 리뷰 문서는 만들지 않는다. 이 변경으로 Pi의 `submit_result` 편집 대상이 넓어진다. 현재는 README 3개만 편집할 수 있다. 앞으로는 `docs/verified-catalog.md`, `docs/catalog-history.md`, `data/catalog-status.json`도 편집 대상에 포함해야 한다.

### 3.4 README 교체 기준

교체 검토는 해당 카테고리의 기존 README 항목 각각을 신규 항목과 비교한다. 교체는 다음 두 경로 중 하나로만 일어난다.

**경로 A: 기존 항목의 명시적 결격.** 기존 항목이 다음 중 하나에 해당한다는 증거가 이번 실행에서 확인되면, 다른 조건과 관계없이 그 항목을 교체한다. 저장소가 archived로 표시된 경우, 운영사가 서비스 종료나 종료 예고를 공지한 경우, 신규 사용자가 해당 제품이나 에디션을 더 이상 사용할 수 없는 경우. "180일 이상 활동 없음"은 성숙한 소프트웨어와 방치된 프로젝트를 구분하기 어려우므로 경로 A에 포함하지 않는다. 이 경우는 5절의 "해석 여지가 있는 교체"로 수동 승인에 보낸다.

**경로 B: 신규 항목의 우위.** 결격 항목이 없으면, 다음 세 조건을 모두 충족하는 기존 항목이 있을 때만 교체한다.

- 포괄: 신규 항목이 기존 항목의 핵심 기능을 포함하고, 기능 범위가 더 넓거나 더 활발히 유지되는 것이 증거로 확인된다.
- 정량 점수 우위: 3.5절의 점수표로 계산한 신규 항목 점수가 기존 항목 점수보다 높다.
- 모델 종합 판단: 모델이 신규 항목이 더 나은 시작점이라고 판단하고, 그 근거를 증거 URL과 함께 구조화된 결과에 기록한다.

경로 B의 후보가 여러 개이면 점수가 가장 낮은 기존 항목을 교체한다.

**보호 기간.** README에 들어온 지 90일이 지나지 않은 항목은 경로 B의 교체 대상에서 제외한다. 경로 A(명시적 결격)는 보호 기간과 관계없이 적용한다. 이 규칙은 같은 카테고리에 요청이 몰릴 때 신규 항목이 곧바로 다시 밀려나는 연쇄 교체를 막기 위한 것이다. 기존 항목의 README 등록일을 기록하는 필드가 현재 `data/catalog-status.json`에 없으므로 구현에서 추가해야 한다. 등록일 기록이 없는 기존 항목은 보호 기간이 지난 것으로 본다(설계자 판단).

**수량 제한.** 자동 등록과 자동 교체 모두 수량 제한을 두지 않는다(메인테이너 결정). 연쇄 교체는 보호 기간으로만 막는다.

### 3.5 정량 점수표

설계자가 다음 점수표를 제안했고, 메인테이너가 2026-10-20에 확정했다. 점수 항목과 기준값은 코드에 직접 쓰지 않고 설정 파일로 분리한다. 그러면 나중에 코드를 바꾸지 않고 기준을 조정할 수 있다. 각 항목은 0-2점이고 합계는 0-10점이다.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 최근 활동 | 180일 이상 릴리스·커밋·문서 갱신 없음 | 90-180일 이내 활동 | 90일 이내 활동 |
| 문서 품질 | 마케팅 페이지만 있음 | 설치·사용법 문서 있음 | 사용법과 레퍼런스 또는 예제 있음 |
| 신규 사용자 접근성 | 대기자 명단·초대제 | 가입 필요 또는 유료만 있음 | 무료 사용 가능 또는 오픈소스 |
| 독립 출처 | 없음 | 1개 | 2개 이상 |
| 카테고리 적합성 | 다른 카테고리가 주 용도 | 부분적으로 맞음 | 카테고리 목적(`categories.mjs`의 `purpose`)과 직접 일치 |

학습 리소스는 기존 정책대로 릴리스 주기가 아니라 내용의 정확성과 사용 가능성으로 평가하므로, "최근 활동" 항목을 "내용의 현재성"으로 대체한다(설계자 판단). 이 항목은 다음과 같이 채점한다. 내용이 다루는 도구나 기능이 현재 사라졌거나 크게 바뀌었다면 0점이다. 일부 내용이 현재 버전과 다르다면 1점이다. 내용이 현재 버전과 맞거나 최근 90일 이내에 갱신되었다면 2점이다. 점수 근거는 항목별로 증거 URL과 함께 구조화된 결과에 기록한다.

**점수 저장(설계자 판단).** 기존 README 항목의 점수는 실행할 때마다 다시 계산하지 않는다. 대신 `data/catalog-status.json`에 항목별 점수, 채점일, 근거 URL을 저장해 두고 재사용한다. 저장된 점수가 90일보다 오래되었거나 아직 없으면, 교체 검토를 할 때 그 항목만 다시 채점한다. 이렇게 하는 이유는 다음과 같다. 현재 `scripts/lib/pi-runner.mjs`는 `search_web` 호출을 실행 1회에 12회까지만 허용한다. 카테고리의 기존 항목 8개를 매번 다시 채점하면 이 한도를 넘는다. 재채점 때문에 한도가 부족해지면 구현자가 한도를 조정할 수 있다.

### 3.6 빠진 항목의 처리

교체로 README에서 빠진 항목은 사유에 따라 다른 곳으로 옮긴다. 경로 A(결격)로 빠진 항목은 `docs/catalog-history.md`에 상태(`archived`, `sunsetting`, `unavailable` 등)와 증거 URL을 기록한다. 경로 B(우위)로 빠진 항목은 여전히 유효한 리소스이므로 `docs/verified-catalog.md`의 해당 카테고리로 옮긴다. 두 경우 모두 `data/catalog-status.json`의 `location`과 `status`를 갱신한다. 세 언어 README와 확장 목록, 이력 문서의 변경은 하나의 커밋에 함께 들어가야 한다.

## 4. 공식 벤더 MCP와 보안 민감 도구의 경계

5절의 "보안 민감 도구"는 범위가 넓으면 자동 등록이 거의 일어나지 않는다. Context 카테고리의 MCP 도구는 대부분 외부 시스템에 쓰기 권한을 가지기 때문이다. 메인테이너는 다음과 같이 경계를 정했다.

서비스 운영사가 자기 서비스를 위해 직접 배포한 공식 MCP 서버나 에이전트 도구는 자동 처리한다. 예를 들어 Prisma가 배포한 Prisma MCP(#47)는 Prisma 데이터베이스에 쓰기 권한이 있지만 자동 처리 대상이다. 이 판단의 근거는 사용자가 이미 해당 서비스를 신뢰하고 있고, 도구가 그 서비스 밖의 자격증명을 다루지 않는다는 점이다. 도구가 "공식"인지는 다음 두 조건 중 하나로 판정한다. 도구의 문서가 서비스 운영사의 도메인에 있거나, 저장소가 운영사의 공식 조직 계정에 있으면 공식 도구다. 이 기준은 설계자가 제안했고 메인테이너가 2026-10-20에 확정했다. 3.2절의 독립 출처 범위도 같은 날 확정되었다. 두 기준 모두 설정값으로 분리한다.

반면 여러 다른 서비스의 자격증명을 대신 보관하거나 중계하는 제3자 도구, 결제 수단을 다루는 제3자 도구, 사용자 시스템에서 원격 명령을 실행하는 제3자 도구는 수동 승인으로 보낸다. 예를 들어 Aident Loadout(#55)은 사용자가 연결한 여러 앱의 자격증명을 보관하므로 수동 승인 대상이다.

## 5. 수동 승인이 필요한 경우

7개 검사를 통과했더라도 다음 중 하나에 해당하면 자동 처리하지 않고 `needs-review` 라벨과 함께 수동 승인으로 보낸다. 봇 코멘트에는 해당 사유의 이름, 판단 근거, 증거 URL을 적는다.

| 사유 | 판정 기준 | 대기 중 예시 |
|---|---|---|
| 보안 민감 도구 | 4절 기준에 따른 제3자 자격증명 보관·중계, 결제, 원격 명령 실행 도구 | #55 Aident Loadout |
| 목록·디렉터리·제휴 사이트 | 다른 도구를 모아 놓은 디렉터리나 awesome-list, 또는 제휴(affiliate) 링크나 후원 유도가 있는 사이트 | #54 AIUseFlow |
| 해석 여지가 있는 교체 | 교체 근거가 "장기 미활동"처럼 성숙한 소프트웨어와 방치된 프로젝트를 구분하기 어려운 경우 | 없음 |
| 근거 충돌·조건 불명확 | 출처끼리 내용이 다르거나, 가격·라이선스·접근 조건을 확인할 수 없거나, 3.2절의 독립 출처가 없거나, URL 읽기가 일시적으로 실패한 경우 | 재처리 후 판정 |

기존 정책의 거절 사유(명백한 범위 밖, 중복, 기만, 악성, 사용 불가)는 그대로 거절로 처리하며 수동 승인으로 보내지 않는다.

### 5.1 /approve와 /reject의 동작

메인테이너가 `/approve`를 코멘트하면, 이 절의 수동 승인 사유는 면제하고 다시 처리한다. 5개 필수 조건, 중복 검사, 3개 언어 번역 검증은 계속 적용한다. 이렇게 정하는 이유는 수동 승인 사유가 모델이 판단할 수 없어서 사람에게 넘긴 항목이기 때문이다. 사유를 면제하지 않으면 재처리 시 같은 사유로 다시 보류된다. 면제 후 배치 결정(3.3절)과 교체 기준(3.4절)은 자동 처리와 똑같이 적용한다.

`/approve`가 "해석 여지가 있는 교체" 사유를 면제하는 경우, 장기 미활동인 기존 항목을 경로 A의 결격으로 간주해 교체한다(설계자 판단). `/reject [사유]`는 기존과 같이 이슈를 닫고 사유를 기록한다.

## 6. 실행 구성

DeepSeek을 새 기본 provider로 `scripts/lib/pi-config.mjs`에 추가한다. 기존 Kimi와 Qwen은 `AI_PROVIDER` 환경변수로 계속 선택할 수 있게 유지한다. 기본값 변경은 이슈 처리와 주간 업데이트 모두에 적용된다. 모델 ID는 기존 방식대로 `AI_MODEL` 환경변수로 덮어쓸 수 있어야 한다. DeepSeek API의 정확한 base URL, 모델 ID, API 키 이름(예: `DEEPSEEK_API_KEY`), OpenAI 호환 여부는 이 문서에서 확인하지 않았으므로 구현 시 DeepSeek 공식 문서로 확인해야 한다. 조직 시크릿에 API 키를 등록하는 작업은 메인테이너가 해야 한다.

## 7. 대기 중인 7건의 처리

정책 구현이 끝나면 대기 중인 7건(#47, #49, #53, #54, #55, #56, #58)을 새 파이프라인으로 자동 재처리한다. 단, 재처리는 메인테이너가 DeepSeek API 키를 조직 시크릿에 등록한 다음에 실행한다. 키가 없을 때 Kimi로 대신 재처리하지 않는다. 재처리 결과는 바로 main에 커밋되고 교체도 일어날 수 있어 되돌리기 어렵기 때문이다. 재처리 방법(워크플로 수동 실행, 라벨 재부착 등)은 구현자가 정한다. 같은 Context 카테고리에 5건이 몰려 있으므로 처리 순서가 결과에 영향을 준다. 이슈 번호 오름차순으로 처리하고, 앞선 요청이 README에 들어가면 90일 보호 기간이 적용된다(설계자 판단).

## 8. 완료 기준

다음이 모두 충족되면 이 정책의 구현이 완료된 것으로 본다. `docs/curation-policy.md`와 `docs/automation.md`가 이 문서의 정책을 반영한다. Pi에 전달하는 프롬프트(`.github/prompts/`)와 결과 검증 코드가 확장 목록 등록, 교체, 수동 승인 사유를 구조화된 결과로 다룬다. 교체 기준, 보호 기간, 독립 출처 요구, 수동 승인 사유 판정은 모델 출력만 믿지 않고 코드에서도 검증한다(점수 합계 비교, 보호 기간 계산, 증거 URL 관찰 여부 등 코드로 확인할 수 있는 부분에 한함). `npm test`가 통과한다. 대기 중인 7건이 재처리되어 각각 등록, 확장 목록 등록, 교체, 수동 승인, 거절 중 하나의 결과를 가진다.

## 9. 구현자에게 맡기는 사항

다음 사항은 구현자가 정한다. 워크플로 트리거 구조와 구조화된 결과의 필드 이름을 정한다. 90일 보호 기간에 쓸 등록일 필드의 이름과 점수 저장 필드의 이름을 정한다. 기존 항목을 새 필드로 옮기는 마이그레이션 방식을 정한다. 대기 중인 7건의 재처리 실행 방법과 기준값을 둘 설정 파일의 위치와 형식도 정한다.
